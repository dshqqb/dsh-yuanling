# 原灵 yuanling

可以自行成长的DSH长期记忆与人格底座，松耦合，模块化， 纯文件、纯 JSON，没有数据库，没有向量库，没有后台服务依赖。

1. 松耦合：

   插件的数据目录可在安装时指定，所有数据+设置+模块都放置于该目录，可以简单地通过复制粘贴来迁移。

2. 模块化：

   核心框架只保留最基本的记忆相关设置，只负责对数据进行处理，从模块接受数据，发送数据给大模型，记录数据到原始层。

   对接QQ、B站、桌宠等功能都采用模块化的方式，每个模块是单独的项目，安装之后放置于yuanling数据目录的模块子目录下，可以卸载、更新、导出配置。

   模块可以有自己的设置页面。

3. 长期记忆与自行成长：

​	原始层：即原始数据，从所有模块获取的数据原封不动保存于原始层（写过一次之后只读，不可改）

​	虚拟人格：	

​	A. 人格层：基础骨架由人设定，不能自改，表达层内容可以由大模型自行演化，共同塑造虚拟人格，并可由用户自行决定这些演化是否生效和控制人格演化速度。可切换人格卡，人格卡下的所有数据（包括记忆、动机、人物、群体、规则）放置于同一目录，可通过复制粘贴来迁移人格。人格有唯一的ID，但有多个名称，名称可以由用户填写，也可以由虚拟人格自行塑造（如有人多次用一个昵称称呼虚拟人格，虚拟人格接收后就可以将昵称写入人格卡）

​	B. 记忆层：所有内容由虚拟人格通过原始层生成，结合人格层内容解读，并形成专属于虚拟人格的记忆，同一事实，不同虚拟人格的记忆可能不同，这是被允许的，更加有真实感，记忆通过指针指向真实存在的原始层数据，记忆层里的内容可以被虚拟人格提取并用于交流。

​	C. 动机层：人格层塑造了虚拟人格被动的方面，动机层则塑造了虚拟主动的方面，虚拟人格可以被动机驱使主动去做一件事，动机可以由虚拟人格自行修改权重，更感兴趣的、接触更多的权重就会逐渐上升，也可以由虚拟人格自行添加新的动机。

​	D. 人格塑造：对虚拟人格反复提及的事会在记忆里形成提案，并在通过之后作用于人格层的表达层部分，用于塑造虚拟人格，用户可以否决或回滚提案，提案有等待时间，也有每天的上限，以免虚拟人格被改变得太快。虚拟人格也可以通过添加新的动机、修改动机权重，来塑造虚拟人格主动的方面。	

​	E. 人物卡：虚拟人格对一个网络账户的印象和描述，可由虚拟人格从原始层+记忆层之中自行整理出来，也可以由用户自行添加，一个网络账户（如QQ号，B站ID）对应一张人物卡。

​	人物卡包含如下内容：1. 人物卡id（唯一标识）  2. 关联账户（列表）  3. app标识  4. app账户（id或账户名）   5. 初识时间      6. 账户描述    7. 账户权重  8. 账户昵称（可为多个，中间用空格分隔）

​	其中 3到8为账户相关，用于描述这个账户的相关内容，如初始时间为第一次跟这个账户发送信息的时间，虚拟人格可以根据与该账户的聊天内容和自己的理解来自行修改和演化人物昵称和账户描述。2在人物卡只有一个账户时为空。 

​	当一个账户与虚拟人格产生对话（群聊里艾特或私聊或回复过虚拟人格或被虚拟人格主动艾特和回复）则为其新建人物卡，成为好友，并按照交流次数和印象程度进行权重排序。也可以由用户手动指定重要人物。

​	与该人物聊天或聊天中涉及到该人物时。虚拟人格可以调出人物卡放在上下文中供参考。

​	当多个不同的人物卡确定为同一人物的两个账户时，由虚拟人格进行合并（也可以由用户指定合并），合并之后，只保留一张人物卡，隐藏其他人物卡。权重通过几张人物卡的账户权重计算出来。

​	F. 群体卡：与人物卡类似，同样是个抽象的概念，虚拟人格对某个群体的印象和描述，群体可以是贴吧、QQ群、微信群等任意APP社交群体，不同APP讨论同一件事的两个群，视为不同的群体，不会跟人物卡一样合并。虚拟人格可以自行修改和演化对该群体的描述，当在该群体之中聊天或聊天时提及该群体时。yuanling可以调出群体卡放在上下文中供大模型参考。群体卡名称唯一，但可以有多个昵称，用自然语言记录在群体卡描述文字中。

​	H. 规则：可以设置虚拟人格读取和发送信息的各种规则、包括全局规则、群体规则、人物规则。

yuanling的目标不是"记住更多"，而是**成长----记住的东西能被解释、被纠正、被忘掉**。

## 它站在谁的肩膀上

设计这块的时候读了七个现成项目（都是 DSH 生态里的记忆/人格插件），逐个拆开看哪些机制经得起推敲、哪些是过度设计。下面这张表就是当时的结论——**左边是拿走的，右边是明确不要的**。

| 项目 | 采纳的 | 放弃的 |
|---|---|---|
| [dsh-memory-dict](https://github.com/Sleepless256/dsh-memory-dict) | 文件夹 + 纯文本 + JSON 的存储形态；**扁平词条**（一个主题写透，不拆碎、不建层级）；槽位（同槽位新值关闭旧值）；三层查重（全同 → 包含 → bigram ≥ 0.78）；原子写（临时文件 + rename）；常驻预算硬上限 | **全人工写**——每条记忆都得手动敲，用三天就没人写了；**没有时间线**——只知道"现在是这样"，不知道"从什么时候起、到什么时候止" |
| [surfcore](https://github.com/Mieksido/surfcore) | 拟人遗忘（四级清晰度）；**「最初」机制**（30 天窗口 + 确定性散列，不是随机抽签）；单一写者模型；scope 隐私隔离；回环 + 令牌的管理台；摘要与全量分离；B站只读的边界姿态；**目的层**（见下） | **把 `clarity` 存成字段**、每天降一档——某天定时任务没跑，就永远不降了。原灵改成**纯函数派生**：不存在"漏跑"这回事；**2284 行动机机**（9 维需求 + 中文关键词表 + 目标假设树 + 正则读回执）——那是为"单独开模型回合"服务的，我们用不上 |
| [dsh-soul](https://github.com/icyaaaww/dsh-soul) | 作废不删行；`valid_to / supersedes` 双时间线；变更计划（先列变更、再落盘） | 多档状态机；把"整理"做成一套需要人伺候的流程 |
| [dsh-agent-soul（ECHO）](https://github.com/cyanwell/dsh-agent-soul) | **没有指针不许进长期层**——这条被原灵当成第一硬规则；只追加账本（append-only） | 全量卡注入——把整本记忆塞进上下文，token 烧得比聊得还快。原灵默认 **8 KB**（1M 上下文下占 0.5%），并且明写裁剪顺序 |
| [canyueY/dsh-mnemosyne](https://github.com/canyueY/dsh-mnemosyne) | 观察 → 证据 → 记忆的认知链；事实与推断分离；**好评/自评不作晋升依据**；每次结构变更有日志 | **Claim 九态**（提议/支持/合格/已验证/争议…）——一个人自己的记忆不需要九个状态，三档 + 证据 + 时间线足够；**23 个 migration**——迁移脚本比功能还多，说明模型没想清楚 |
| [DSH-Raising-Plan/dsh-mnemosyne](https://github.com/DSH-Raising-Plan/dsh-mnemosyne) | 兴趣信号分层（被动 / 注意 / 投入 / 明说）；**单次观察永不晋升**；`oppose_discount < 1`（一次反驳抹不掉大量一致证据，但明确否定可触发复核）；内容哈希做幂等键；删除级联 | 重 schema 与强状态机——原灵的状态就是一个字段（`until` 有没有值），其余用时间线和证据表达 |
| [xiaoman-memory](https://github.com/yunkong-134/xiaoman-memory) | **沉底**：离开常驻与默认检索，权重随时间衰减，但不删 | 用"沉底"替代遗忘语义——沉底只解决"别占位置"，不解决"该不该记得" |

### 从 surfcore 学到的目的层：学了什么、改了什么

surfcore 有一套完整的"目的引擎"（`purpose-engine.js`，2284 行）。它的结论是对的：**活人感不来自频率，来自"每条开口都有来处"和"没说完的话"**。原灵拿走了机制，砍掉了一半的复杂度。

| 维度 | surfcore | 原灵 |
|---|---|---|
| 需求维度 | 9 维 + 一张中文关键词表 | **5 维**（陪 / 关心 / 好奇 / 分享 / 自我），信号取自记忆主题与互动间隔——不再维护词表 |
| 欲望变化 | 半衰期 8 小时回落基线 | **12 小时**（对话密度更低，慢一点更像人）；`connect` 随"多久没说话"每天 +0.4 |
| 目的来源 | 素材摘要 → 种子 + 目标假设树 | **记忆事实**（带情绪或带槽位、6 小时~7 天前）→ 目的账本 |
| 能不能解释 | 素材是摘要，答不出"为什么问这个" | **每条目的带 `origin` 指针**，能翻回 raw 里那句原话 |
| 怎么说出口 | 单独开一个模型回合 + 正则解析 `【待续】` 回执 | 写进卡片 `[惦记]`，**同轮回复里自然带出**——零额外调用 |
| 防重复 | 三重去重 + pending 14 天 | 6 小时冷却 + 提够 2 次自动放下 + 一轮内相似去重 |
| 没说完的话 | 靠模型自己写 `【待续】` | 账本里 `open` 状态 + 14 天 TTL，到期没提就 `dropped` |
| 主动性 | 独立调度器 + 十道闸门 + 双载体 | 复用 `rules.action` 闸门；外发留给 `dsh-yuanling-qq` 模块 |

一句话：**它证明了这件事值得做，也证明了不用写 2284 行。** 原灵用约 300 行做到它的主干，靠的是两样它没有的东西——能回到原话的记忆，和本来就在跑的 agent 回合。

### 刻意不学的三件事

1. **不用向量库 / 嵌入。** 检索靠 bigram 相似 + 重要度 + 时间，几百条事实完全够用；上了向量就要解释"为什么召回这条"，而原灵要求**可解释**。
2. **不用数据库。** SQLite 也能用，但换机器、备份、人肉查看、git diff 全都变麻烦。文件夹 + JSON 的代价是性能，收益是**你能用记事本打开它**。
3. **不调用模型。** 提取、评分、演化全在本地算，零 API 调用。所以"她为什么记得这个"永远能答——不需要再问一次模型。

## 它解决什么

| 问题 | 常见做法 | 原灵的做法 |
|---|---|---|
| 记不住 | 只保留最近 N 轮 | 原始层永久留档，记忆层按重要性分层衰减 |
| **记错了却改不掉** | 摘要越摞越多，错的一直在 | 每条事实必须挂一个 `raw/…#ULID` 指针，可回查、可回滚 |
| **该忘的忘不了** | 删除即破坏，或者根本删不干净 | 墓碑：不动 raw，只在所有出口隔离，可撤销 |

一句话：**没有指针，就不许成为事实。**

## 设计框架

```
┌─────────────────────────────────────────────────────────┐
│  模块（独立进程，各自独立仓库）                            │
│  qq / bili / 你的模块 …                                   │
│  只能说协议：ingest / propose.fact / media.* / send       │
└───────────────┬─────────────────────────────────────────┘
                │  只有「协议」这一条接触面；核心是唯一写者
┌───────────────▼─────────────────────────────────────────┐
│  L0 原始层  raw/YYYY-MM/DD/<source>.ndjson               │
│  只追加、不改写、按天封存、sha256 日链                    │
└───────────────┬─────────────────────────────────────────┘
                │  证据指针（唯一入口）
┌───────────────▼─────────────────────────────────────────┐
│  L1 记忆层  personas/<id>/spaces/**/<主题>.json           │
│  事实 = 文本 + 指针 + 重要度 + 槽位 + 人生周期             │
│  三带：最初 / 最深刻 / 最新                               │
└───────────────┬─────────────────────────────────────────┘
                │  反复出现 → 提案
┌───────────────▼─────────────────────────────────────────┐
│  L2 人格层  SELF.md（骨架，不许自动改） / style.md（可演化）│
│  实体档案  entities/cards|groups                         │
└───────────────┬─────────────────────────────────────────┘
                │  记忆里"没说完的事" → 目的
┌───────────────▼─────────────────────────────────────────┐
│  L3 目的层  self/drives.json / self/purposes.json         │
│  想要什么 → 想说什么 → 这一轮说哪句（[惦记]）              │
└─────────────────────────────────────────────────────────┘
```

**核心与模块的关系是单向的**：模块把看到的东西交给核心（L0 → L1），核心把"要发什么"交给模块（`send`）。模块**不能**直接写 raw、不能直接写记忆、不能自己决定发什么——这是协议的四个硬边界，也是"她不会背着你说话"的落点。

**原始层只保证一件事：记下来的，跟收到的，一致且没丢。**

- 它**不判断真假**。群友说"我昨天去了北京"就是一条记录，不是一条待核实的论断——谎言也是交流的一部分，可不可信要看上下文和人，不该由一层存储盖章。
- 它**不做可信度分级**。对原灵来说所有原始数据都来自外部（QQ、B站、按需抓的网页），给某几类标"外部数据"等于给整个记忆库降级。
- 凡是被改过的地方都留痕：超长截断（`truncated`）、脱敏、跳过的条数（只记数不记内容）。真实与否留给提炼层和模型，保真归原始层。

三条线**贯穿所有层**：

- **版本线**：任何写盘都进内容寻址的 blob + append-only journal，回滚是"生成新版本"，不是"抹掉过去"。
- **规则线**：`guardrails.json`（硬线）→ `rules/ingest.json`（入库）→ 人格级 `rules/`（recall / action / persona）。
- **能力线**：模块声明能力 → 人授予 → 核心在每次请求上校验（未授予回 `E_NO_CAP`）。

**边界很硬**：规则只管"能不能做"，从不塑造人格。人格靠记忆与表达层慢慢长出来。

## 一轮对话发生了什么

### 写入

```
QQ / B站 / 桌宠 / DSH
   │  ① 投递（NDJSON 文件 或 回环 HTTP + token）
   ▼
inbox  →  ② 硬线检查（guardrails.never_record 命中就丢弃，只计数）
   →  ③ 脱敏（密钥无条件打码；软黑名单入库但标 hidden；显式 skip 不落盘）
   →  ④ 追加 raw（补齐 v / id / h，32MB 自动分片，单行 256KB 截断）
   →  ⑤ 封存（day.json：行数 / 字节 / sha256 / 前一日哈希）
   →  ⑥ 群频道（`group:` / `tieba:` …）顺手记一笔群体：第一次见到就建卡，
         之后只在隔了 30 分钟以上时推「最后一次见到」——不为每句话造一条版本
```

### 自动提炼（入库时，规则表，不调模型）

大部分事实不需要谁专门去写：消息进来时就顺手提炼了，但**只提炼"跟她有关"的**。

| 场景 | 提炼吗 | 判据 |
|---|---|---|
| 任何私聊 | ✅ 全部 | 私聊天然是跟她说话，谁的私聊都算 |
| 群里提到她 | ✅ 这条 + 之后相关的对话 | 文本里有她的名字（取 `SELF.md` 的「名字」） |
| 群里她开口之后 | ✅ 之后相关的对话 | 她在该群说过话（适配器把她的话作为 `role: bot` 上报时） |
| 群里与她无关 | ❌ | 没被提到、也不在"在场"窗口里 |

"在场"是个窗口：**4 分钟滑动**（只有跟她有关的消息才顺延）、**20 分钟封顶**；
超时就当作另一段对话，下次要有新的触发才重新进入。宁可把对话切成两段，也不把整群闲话吸进记忆。

句式表在 `src/core/extract.js`（身份 / 喜好 / 打算 / 关系 / 情绪 / 叮嘱），是数据不是逻辑，
想多认几种说法加一行就行。提炼出来的事实带 `kind: extracted`、重要度 30，
记忆页上标一个「提炼」标签——**误报总是有的，人得能一眼筛掉**。

> **自动提炼只是兜底。** 它只会把原句机械地摘成一条——同一句话，不同人格应该记成不一样的东西。
> 正途是她**用自己的话写**（`yuanling_remember`）：先看自动提炼写了什么，觉得不准就重写一条，
> 并把旧那条放进 `supersedes`——旧事实不删、历史仍在，只是不再进上下文。
> 这就是"虚拟人格按自己的性格去理解同一件事"落到实处的地方：核心不调模型，理解由她自己给。

### 记成事实（模型或人显式调用）

```
addFact({ topic, text, src: "raw/2026-11/07/qq.ndjson#01JCV...", supersedes: ["fact_…"] })
   │  ① 指针必须能解析到真实记录   ← 硬规则，不满足直接抛错
   │  ② 查重：完全相同 / 包含 / 双字 bigram ≥0.78  → 命中则只 +1 重复次数
   │  ③ 槽位：同槽位新值关闭旧值（写 until，不删）
   │  ④ 替换：supersedes 里的旧记忆标 until（历史仍在，不再进上下文）
   │  ⑤ 重要度：规则表打分（承诺 > 事实 > 闲聊）
   │  ⑥ 情绪浓度、是否「最初」
   ▼
personas/<id>/spaces/日常/<主题>.json  +  版本历史一条
```

规则提炼抓不到、但值得长期记住的事，模型用 `yuanling_remember` 写——同样必须给 `src` 指针；
觉得自动提炼那条不像她自己会说的话，就重写一条并 `supersedes` 掉旧的那条。**记忆是她的话，不是摘录。**

### 注入（每一轮）

```
buildCard()  ≤32 KB（默认，可配）—— 只装记忆，不含人物
  [骨架]     SELF.md：名字 + 存在的原因（≤320 字节，永不裁剪）
  [说话]     SELF.md：语气 / 口癖 / 不做的表达（≤520 字节）
  [在乎]     SELF.md：价值观，按你排的优先级（≤400 字节）
  [硬线]     绝对不做的事（≤640 字节，永不裁剪；超了拒绝保存，不静默截断）
  [习惯]     表达层学来的说话习惯（≤320 字节）
  [最初]     6 条，不衰减、不淘汰
  [最深刻]   16 条（重要 + 被反复召回）
  [最新]     12 条（14 天内）
  [索引]     N 条事实 / M 个主题 / K 条已隔离

contextFor(channel) —— 按"这一轮谁在场"追加人物卡
  [惦记]    最多 2 条、每条 ≤120 字节（想提就提，不想提就别提）
  私聊：对方那张人物卡（不按字节截断）
  群聊：[群体] 当前这个群（被提到别的群才有第二张）+ [人物] 被 @ 的人、最近发言人（最多 8 张）
```

**骨架为什么是三层而不是一份全文**：`[骨架]` 是"她是谁"，`[说话]` 是"她怎么开口"，`[在乎]` 是"冲突时保哪个"。三段都进上下文，因为语气和取舍是最直接影响输出的东西；但每段都有字节上限——骨架不能抢记忆的预算，`[最初] 6 条` 是更硬的底线。SELF.md 里其余段落只给人看，不进注入。

SELF.md 里**只有人能动**；`style.md`（表达层）是她自己可以改的地方——模型可以用 `yuanling_style` 直接改，也可以走"提案批准"那条路。**写进去的每一条都会进上下文**（上限 320 字节，满了要先删），每次改动都进版本历史、可回滚。

**人格的名称可以有多个**（空格分隔，例：`原灵 小灵`）：人格 **id 唯一**，名称不查重——不同 id 的人格可以同名。
每个名称都算在叫她（群里喊任一个都会被她听见），也都会出现在 `[骨架]` 里。人可以在概况页改，她也能自己往名称里加。

**新称呼是她自己发现的**（不是模型猜的）：有人 **@ 她 / 引用回复她** 时，句首那个 2–6 字的称呼会被记一笔；
**不同的人 ≥2、累计 ≥3 次、跨 ≥1 天** 才写进名称（上限 6 个）。已知名字、常用词、以及和人物/群体昵称重名的词都会被挡掉——
写错名字会污染她对自己的认知，所以宁可漏，不可错。攒的过程在 `personas/<p>/state/names.json`，写进去走的是和人工改名同一条路（可回滚）。

**「惦记」是什么**：她的目的账本里到期的那几件事，比如"你上次说面试，后来怎么样了"。每条目的都带 `origin` 指针，能翻回 raw 里那句话——所以被问"你怎么突然问这个"时答得出。它不是日程提醒，是**没说完的话**；写得明确可选，因为尬聊最伤"像不像人"。

防骚扰有三层：**同一件事 6 小时内不重复提**、**提够 2 次自动放下**、**一轮里说的是同一件事只留一条**。

人物卡是**本地档案库，数量无上限**；进上下文的只是"现在在说话的那几个人"。权重不参与这里的选择——它只决定管理台里怎么排。如果群里有 20 个好友，她这一轮也只会带上正在说话的 8 个。

**人物卡优先**：人物卡先占预算、不截断；剩下的预算才给记忆卡，记忆不够时仍按「最新 → 最深刻」裁，永不动「最初」。

所以预算是**软上限**：如果「骨架 + 最初 + 索引」本身就超了，卡片会超预算而不是继续裁——「最初」是她最早认识你的那几件事，宁可多几十字节，也不能把它们挤掉。

> 为什么是 32 KB 而不是 320 KB：1M 上下文下 32 KB 只占 1.2%（按中文算），放得下；但**放得下不等于该放**——注入 100 条平庸记忆，比 10 条关键的更容易让她说错话。预算是用来逼出取舍的，不是用来省 token 的。

**迁移一个人格**：把 `personas/<id>/` 整个复制到目标数据目录的 `personas/` 下就行——
启动（或跑任意 CLI 命令）时会自动认领：目录里有、根标记里没有的人格会被补登记，然后就能在人格列表里切过去。
认领**只增不删**：登记里有、目录暂时没挂载的，不会被删掉；没有 `persona.json` 的半截目录不会被当成人格。
原始层（`raw/`）是所有人格共用的，不跟着人格搬。

**哪些能删**：`system/shields.json` 删了可以从 raw 重建；`system/modules.json` 删了重扫 `modules/` 就能还原；`personas/*/versions` 删了只是丢掉回滚能力；`media/index.ndjson` 删了能从 `media/` 与 raw 里的引用重建。
**不能删**：`raw/` 和 `media/`（含 `media-archive\`）——删了就没有任何东西能证明事实从哪来、那句话长什么样。`raw/` 是文本的真相，`media/` 是二进制的真相；归档删掉之后那些指针就真的找不到了。

**媒体的生命周期**（`media/` 的清理规则）：

- **全留。** 不按年龄删、不按配额删——几十 G 的空间换"她记得的那张图还在"，值。
- **去重是自动的**：同内容同 hash 同路径，群里转发的重复文件不占第二份空间。

**入库（已实现）**：模块把文件写进自己的临时目录（`system/tmp/<id>/`）→ `media.put.file`。
核心校验路径 / 单文件 ≤20MB / mime 白名单 / 每分钟 20 次，算 sha256 落盘、追加索引、收走源文件，
返回 `media:sha256:<hash>.<ext>`。

**出库（已实现）**：`media.get` 把指针解析成**临时文件**（10 分钟过期），帧里不出现内部指针；
**热库没有就去归档库找**——指针永不过期。

**归档（已实现）**：`yuanling media archive [--days n] [--apply]`——默认**只出一份清单**
（多少个、多大、最老到哪年、raw 里被引用几次），加 `--apply` 才真的搬去 `media-archive/`（同 hash 布局）。
搬走之后 `media.get` 仍然读得到；同一内容再次入库会从归档搬回热库，不留两份。
另有 `media stats`（热库/归档各多少）与 `media list`。

**发图（已实现）**：`egress.request` 可以带 `media: [ptr]`——核心校验指针存在、把它换成临时文件
（`{path, mime, size, expires_at}`，10 分钟过期）随放行结果返回；**一条消息最多 9 个**，出站账本只记张数。
帧里永远不出现内部指针。

## 模块

**核心只做四件事**：原始层、记忆层、人格层、规则与版本。对外的每一种能力——QQ、B站、桌宠、语音、视频——都是**模块**，各自独立仓库、独立进程。

| 约定 | 内容 |
|---|---|
| 命名 | `dsh-yuanling-<name>`（推荐，不强制；身份以 manifest 的 `id` 为准） |
| 形态 | 独立子进程 + stdio JSON-RPC，跨语言（Python 的语音/视频模型也能接） |
| 自描述 | 包根 `yuanling.module.json`：`id / api / kind / entry.command / capabilities` |
| 分发 | **发行包 `.tgz`**（不是 clone 仓库）：装的是产物，不跑构建脚本 |
| 安装位置 | **数据目录内**：`system/modules/<id>/`，注册表 `system/modules.json` |
| 日志 | `system/log/modules/<id>.log`，由核心代写（stderr + 关键事件） |
| 导出 | `yuanling module export <id>` → `system/exports/<id>-<version>.tgz`（换机器拷一个文件） |
| 取数（v1.1） | 模块在 manifest 声明 `sources`，核心/模型按需用 `source.fetch` 向它要一次数据，**取回的东西先落 raw 再给人用** |

**四条硬边界**（模块再强也越不过去）：

1. 不能直接读 `raw/` —— 只能调 `ingest()`，落盘与脱敏由核心决定（`source` 由核心盖章）；
2. 不能直接写记忆 —— 只能提交候选事实，由核心决定入不入库；
3. 不能决定媒体存哪 —— 只能 `media.put.file()`，拿回一个内容寻址的指针；要发图时交回这个指针，由核心换成临时文件；
4. **不能自己决定发什么** —— 主动说的由核心算好放进 `outbox`（模块取走才发），回复要先过 `egress.request`（核心查完规则/名单/配额才放行）；模块只做投递。

第 4 条在代码里的落点是**能力授予**：模块 manifest 里声明 `send`，但**只有被授予后**才能收到 `send`；未被授予时核心直接回 `E_NO_CAP`。能力清单是**封闭词表**（协议 §5.3），写个词表外的能力会被拒装。

**装完是空授权**（协议 v1.1）：安装时把声明的全部能力列一次，问一次"是否全部授予"——一次决定，不逐条勾选（逐条只会让人闭眼按回车）。答不授予也不拦安装，模块装上空转，随时补授。非交互环境（管道、CI）默认按"不授予"处理，要放行必须显式 `--grant`。

### 模块怎么管

```powershell
yuanling module list                     # 列表（含状态与已授予能力）
yuanling module show qq                  # 详情（配置、日志尾巴）
yuanling module install --url <库的网址>    # 填 Gitee/GitHub 仓库地址即可：核心去它的发行版里找 .tgz
yuanling module install --url <tgz直链>    # 也可以直接给包地址（https；http 仅限本机）
yuanling module install --file <本地.tgz>  # 从本地包装（--grant 表示非交互直接授予）
yuanling module grant qq send off         # 收回发消息权限
yuanling module grant-all qq --yes        # 一次性授予它声明的全部能力
yuanling module disable qq                # 停用（重启 DSH 也不会自动启动）
yuanling module export qq                 # 导出 tgz，换机器用
yuanling module uninstall qq --yes        # 卸载（删目录与配置）
```

管理台的「模块」页分三层：左侧菜单最上面是**控制台**（已装 / 运行中 / 崩溃 / 停用的数量，以及安装框），下面是每个已安装模块（显示模块自己在 manifest 里写的 `name`，最多 16 字；有新版会挂一个版本角标）；点模块名进它的详情，分 tab：**概况**（状态、操作、能力开关、规则与配置）、**日志**，以及模块自己声明的页面。

**模块能给管理台加页，但只能加"数据"，不能加"界面"**（协议 v1.2 / v1.3）：manifest 里声明 `ui.tabs`，`kind` 是封闭的四种——`kv` / `list` / `text`（模块回数据，核心画）、`config`（这页就是它的配置表单，核心自己渲染）、`records`（模块只说"看我自己产生的哪类记录"，**核心查自己的原始层**）。模块给不出 HTML / JS / CSS——管理台握着 `console.token`，能读全部记忆、改规则、卸模块，这条线不能松。

`records` 这一型值得单独说：点赞这类记录本来就在 `raw/` 里，让模块再读出来返回等于让它读原始层（违反第一硬边界）。所以方向反过来——核心查、核心画，并**强制按声明它的模块 id 过滤**，模块借这页看不到别人的记录；模块停着也能看。

**配置是表单，不是手改 JSON**：模块在 manifest 里声明 `config.schema`，页面按 `x-widget`（或类型推断）渲染 **8 种控件**：开关 / 勾选 / 单选 / 下拉 / 滑块 / 输入 / 多行 / 列表（列表能增、删、改、调顺序）。名字像密钥的字段用密码框。保存前核心按 schema 校验（必填、类型、枚举、数字量程、列表逐项），保存后**自动重启该模块**让新配置生效——所以填 B 站 cookie 不用再手写 `system/modules/bili/config.json`。

> `action`（按钮）与 `file`（浏览文件）目前是**占位控件**：只画、不校验、不落盘。按钮待 `ui.action` 协议，浏览文件要核心出面开对话框（浏览器拿不到本机真实路径）。

**装完会自动拉起**（v1.1 起）：不用再重启 DSH，装好就能看到"运行中"。授予能力、点「启用」同样会尝试启动。装完会弹一个窗，把模块申请的能力一次列全，你点「全部授予」或「先不授予」——不逐条勾选，因为逐条只会让人闭眼按回车。填库的网址时核心会去它的发行版里挑 `.tgz` 资产（源码 `.zip` / `.tar.gz` 不认）；查不到发行版会告诉你下一步该做什么，不是"点了没反应"。

**「检查更新」**：模块详情里手动查一次（只查发行版元数据、不下载包），有新版弹窗问你要不要更新；进模块页时也会自动查一次，**6 小时内不重复**，只打角标不弹窗。更新是覆盖安装，**模块配置会跟着保留**——cookie 不该因为升个版本就白填。

**「停用」是真的停**：不只是改注册表。停用会停进程、界面如实显示"已停止"；启用会重新拉起。之前只写注册表，结果点了两次都像"没反应"。

**已经能装的模块**（都是独立仓库，原灵只认协议）：

| 模块 | 库的网址 | 干什么 |
|---|---|---|
| `bili` | `https://gitee.com/dshqqb/dsh-yuanling-bili`（[GitHub 镜像](https://github.com/dshqqb/dsh-yuanling-bili)）· `app: "bilibili"` | 只读：搜视频、拉官方字幕；她可以主动向它要数据。管理台里会多出「规则」「点赞记录」两页 |
| `qq` | 本地 `dsh-yuanling-qq 0.2.2`（仓库尚未建）· `app: "qq"` | OneBot v11 网关（SnowLuma 已真机跑通，NapCat 可选）：收消息入 raw、主动开口（outbox）、**回复**（私聊每条；群里只在她被 @ / 引用回复 / 被叫名字时回，并 @ 回说话人）；随消息上报群名与"是不是好友" |

**模块上报 App（v1.8）**：模块在 manifest 里写 `app`（只允许小写字母/数字，如 `qq`/`bilibili`/`milan`），
安装时记进 `system/modules.json`。多个模块可以接同一个 App（NapCat/SnowLuma 都写 `qq`）；
账户卡的 `app` 用这个值，新建人物时从已装模块上报的 app 下拉里选，不能手填。
不再单独维护 app 表——`modules.json` 是唯一权威，读时反转即可。

**QQ 模块的回复闭环**（2026-11-12 真机验证）：模块自己连 DSH（`~/.dsh/.credentials.yaml` 的
`browser-session` 密钥离线铸 Cookie、`netstat+tasklist` 发现端口）→ `session/create`（预设 `yuanling-qq`，
由本包 `presets/yuanling-qq.patch.yml` 注册，**没有本地工具**）→ `session/prompt` → 收回合最终文本
→ `egress.request` 过闸门 → `send_private_msg` / `send_group_msg`。
**核心仍只决定"能不能说"**：回复内容来自会话，主动开口仍由核心算好放进 outbox。

## 人物

她认识的人只有一种卡：**人物卡**。每张卡对应一个账户（app + account），
多张卡属于同一人时，成员表只写在**主卡**上（管理员那张永远是主卡，否则取 id 最小的一张），列表也只显示主卡。
**没有名册、没有"路人"**：没跟她单独说过话的账号，这里什么都不留。

| 问题 | 存在哪 | 为什么 |
|---|---|---|
| **这个账户是谁**（app / account / 昵称 / 描述 / 权重 / 初识） | `personas/<p>/entities/cards/<id>.json` | **按人格**：同一个号在不同人格里可以是不同的人——这是认知，会有误差 |
| **这些账户是不是同一个人**（主卡成员表） | 主卡上的 `members` | 只存一份，避免多副本同步 |

排序三档：**管理员 → 重要人物 → 好友（按权重）**。权重**不能手改**：账户是互动分（0–100），
人物 = 成员卡权重之和（封顶 100）；重要人物按名次计分（110 起、每名 +5），覆盖派生值。

> 这套排序**只作用于管理台的列表**，不决定谁进上下文。上下文里出现谁，看的是"这一轮谁在场"。

### 人物卡：每账户一张 + 主卡成员表

| | 单账户 | 多账户（合并后） |
|---|---|---|
| 卡的数量 | 1 张 | N 张（每个账户一张） |
| 成员表 | 空 | 只在**主卡**上（管理员优先，否则 id 最小），列出所有卡 id |
| 列表 | 显示这张 | 只显示主卡，其他卡隐藏 |
| 账户描述/权重/昵称 | 各卡自己维护 | 各卡自己维护，合并/分离不变 |
| 人物描述 | 该卡账户描述 | 成员卡账户描述按卡 id 升序拼接（不设上限） |
| 人物权重 | 该卡权重 | 成员卡权重之和，封顶 100 |

> **没有"路人"这个概念**（2026-11-14 定）：只在群里见过、还没单独说过话的账号，什么都不记
> （不建卡、也没有名册）。私聊过、被 @ / 引用 / 叫名字之后才建卡——卡 = **好友**。
> 管理员固定是 `dsh:master` 那张卡；"重要人物"是卡上的 `pinned`。

**好友关系不单独存字段**：好友备注写成 `好友备注：…` 一行，放在账户描述里。
**管理员/重要人物/黑白名单只存在主卡上**；主卡换人时跟着成员表一起搬走。管理员永远是主卡。

**没有"人物改名字"这回事**：改称呼就是改账户卡昵称。提到一个人时，先按昵称/账号找到**卡**，再通过成员表归到主卡。

> 群聊里"叫她的名字"用的是 `SELF.md` 的「名字：」那一行（可多个，空格分隔）；@ 她按 Bot 自己的号识别。

### 昵称、以及"这句话在说谁"

| 概念 | 规则 |
|---|---|
| **昵称** | 存在**每张人物卡（账户）**上，可以多个（空格分隔），**允许重名**。账户描述里显式写的「叫 / 昵称 / 外号…」也进称呼索引 |
| **人物名** | 没有独立人物名；显示名 = 主卡昵称（合并时也可以看成员昵称） |
| **提及 → 卡片** | 昵称/账号先命中**卡**，再通过成员表归到主卡。同一昵称命中多个不同主卡时，用“谁在这个群”裁决，裁决不了就跳过 |
| **带几张** | 最多 2 张，**排在在场者之后** |

> 昵称可以重复，是因为现实里称呼本来就重复；确定性靠“先找卡、再归主卡”和群成员裁决，而不是全局唯一名。
>
> 称呼索引**按人格缓存**：指纹取“卡片注册表 + 所有卡文件”的 `mtime + size`，文件一变就重建；
> 没变时只做 `stat`（不读内容、不跑正则）。没有 TTL——这里只有"文件改了才失效"，没有"时间到了就过期"。

### 跟谁说话：白名单 / 黑名单

人物页与群体页最上面各有一对名单。**它们只影响她回不回话，不影响她接收信息**——
raw 照记、记忆照长，只是名单外的人等不到她的回复。

| 开关 | 含义 |
|---|---|
| 都关（默认） | 不限制 |
| **白名单**开 | 只跟名单上的人/群说话 |
| **黑名单**开 | 除名单之外都可以 |

两个开关互斥（打开一个自动关掉另一个）；同一个人也在两个名单里互斥（设进一边会自动离开另一边）。

**管理员、重要人物、重点群体永远在白名单里**，并且**不能被设为黑名单**——这是动态豁免：
取消重点 / 卸任之后豁免自动消失，不需要清理任何数据。

核心不发消息，所以判定由 `canReply()` 给出供适配器查询；**主动开口**（待发队列）会先过这一关。
真正的"不回消息"由适配器执行——名单是策略，不是拦截器。

管理台的人物页分三段：**管理员（固定 1 格）→ 重要人物（↑↓ 调名次，无上限，名次决定权重）→ 好友（按权重）**。权重只读，只能靠互动和“设为重要”来改。`pinned` / 黑白名单只存在**主卡**上（按人格）。**管理员固定在 `dsh:master`（安装时建的第一张卡）**：不可卸任、不可换人、不能设为重要人物；合并时永远是主卡。

**权重的口径**：每张卡只算**和 AI 的互动**（私聊里跟她说的话算，群里跟别人说的话不算），
公式：`消息数×0.5 + 活跃天数×1.0 + 近30天消息数×0.3`，封顶 100。
人物权重 = **成员卡权重之和，封顶 100**；合并/拆分**不改账户权重**，只重算人物。重点人物按名次 110 起，覆盖派生值。

**卡就是账户**：`app + account` 一张卡；新建人物时从已装模块上报的 app 里选，填账户与昵称即可。
两个账户是同一人时用 `yuanling_person_merge` 合并（成员表写进主卡——管理员那张优先，否则 id 最小）；
合并错了用 `yuanling_person_split` 拆开——账户权重/描述/昵称原样跟着卡走。

**管理台里怎么改**（人物页）：

| 操作 | 在哪 | 说明 |
|---|---|---|
| 新建人物 | 「新建人物」 | App 下拉（已装模块上报的）→ 账户 → 昵称 → 描述；一个账户一张卡 |
| 改这个账户 | 卡片后面的「账户 <账号>」 | 标题显示 `app:账号`（例如 `账户 qq:12345`），改的是这一个账户的昵称和描述 |
| 改这个人物 | 点卡片本身 | 主卡昵称/描述、权重、设为重要、黑白名单；合并进来的账户列在下面，可**分离**（先确认，不删数据） |
| 合并两个人物 | 「合并」 | 两级选择：先选 A 的 App→账户，再选 B 的 App→账户；一次请求拿齐候选（`/api/picker`），换 App 只是内存过滤 |

### 印象：她怎么看她认识的人

账户描述（`description`）就是"她对这个账户的印象"；人物描述由成员卡描述合并，不再单独存。规则只有四条，**账户卡和群体卡完全一致**（同一个核心模块、同一个 MCP 工具 `yuanling_observe`）：

1. **整段覆盖**，不是追加。印象回答的是"现在怎么看他"，不是日记；增量拼接会越写越长、旧印象删不掉，最后被预算截在半句话上。
2. **旧版本只留在版本历史里**（`personas/<p>/versions/`），任何一版都能回滚——回滚本身也是一次新版本，不擦掉后来的记录。
3. **每次必须写 `reason`**：这次为什么改。它连同时间、谁写的（`model:observe` / `human:editor`）一起进 journal，所以模型能读回"我为什么现在这么看他"。
4. **账户描述上限 2000 字符**（人物描述本身不设上限）；群体描述上限 600 字节。超了**直接拒**，不静默截断。

人可以随时覆盖（管理台的编辑框、`yuanling person account --description`），模型下次再写就是一版新的，两边都在同一份历史上。主笔是模型，人负责纠偏——写坏了回滚一版就行。

## 群体

「一群人」也是实体，和人物并列管理：一个 QQ 群、一个贴吧、一个粉丝群，各是一个群体。

| 一个群体记什么 | 怎么来的 |
|---|---|
| 平台 + 标识（`qq:123456`） | 从频道推出来，客观；新建/编辑时是「App 下拉 + 群号输入框」 |
| **它是什么地方**（`feature`） | 自然语言，谁来写都行——她总结，你也可以改 |
| 常出现的人（`members`） | 消息进来就记一笔（只收能对上人物档案的人，上限 60）；编辑弹窗里可**手动加人/移除**，也可从原始层重新归集 |
| 互动计数（`stats`） | 入库时判定一次：只记"跟她有关"的互动，权重按它现算 |
| 权重、重点群体 | 和人物一样：自动计分（**写时记**）；**权重不能手改**，设为重点后按名次算（110 起） |

**群体不跨平台合并**，这是和人物相反的地方：同一个人的 QQ 和 B站 号可以合并成一个人，但一个 QQ 群永远不可能和同一个贴吧是一个地方。群体编号是内部编号 `grp_xxx`，平台与群号存在 `entities/group-identities.json`（**按人格**），所以场景里不出现外部号码，将来接新 app 也不用改历史数据的语义。

**群体什么时候出现**：第一条群消息投进来就建卡（`lastSeen` 记这条的时间）；之后的只往前推 `lastSeen`，而且**隔满 30 分钟才写一次盘**——那是给人看的粗粒度信息，不值得为每句话造一条版本记录。去重的那条完全不动它。控制台启动时还会**回填**一次——扫一遍 `raw/` 里出现过的群频道，把装上插件之前就有的历史群补出来（幂等，只读频道与时间，不碰正文）。所以"装好就能看到列表"，不用等下次有人在那个群说话。

反过来，**认不出的频道一律不建**：`private:10001` 是一对一、`module:bili.search_video` 是一次调用、`bili:video:BV1xx` 是一个视频，它们都不是"一个地方"。白名单写在 `GROUP_KINDS` 里，将来接新平台要显式加一行——宁可少一个群，也不让一次调用变成一个地方。

注入的规则是"**只查当前在场的那个群体**"：在哪个群说话，就带那个群的卡；私聊不带。只有一种例外——群聊里有人提到了**另一个**群的名字，这时两个一起查（最多 3 张）。所以上下文里不会平白多出一堆她待过的群。

成员是**事实，不是印象**：她不能编"这个群有 200 人"，只能报告"归集到几个我认识的人"。没归集到就留空，界面上也不编数字。
成员表记的是"谁在这里说过话"：手动移除的人**下次一开口还会自动加回来**（它不是黑名单）。

**管理台里怎么改**（群体页）：新建时同样是「App 下拉 + 群号输入框 + 描述」；编辑弹窗里可以改 App 和群号
（改号会同步改身份登记，`gid` 不变、印象/成员/权重都留在原卡上；**改号之前的群聊记录仍按旧号归档**），
成员一行一个显示「第一个昵称 · app:账号」，带「移除」；下面的「添加人物到群里」用 App → 账户两级选择把人加进来。

群体描述（`feature`）走的是**和账户描述同一套规则**（见上面「印象」）：整段覆盖、旧版本进历史、每次必须写原因、600 字节上限，工具也是同一个 `yuanling_observe`（`kind: "group"`）。

> 权重口径和人物一样：`互动次数×0.5 + 活跃天数×1.0 + 近30天互动次数×0.3`，封顶 100。但**这个"互动"只算跟她有关的**（用户 2026-11-14 定）：有人 @她 / 叫她的名字 / 引用回复她、她自己发言、以及她还在场时别人接的话；群里刷无关的话不涨。新建群体权重 **0**，没有默认分。
> 计数**写时记**（进 `raw` 的那一刻 +1，存进群卡 `stats`），不再读时扫 `raw/`——列表打开更快，也不会因为几十天的闲聊把权重虚抬上去。**权重不能手改**：想抬高一个群就设为重点（名次决定 110 起的分）。群再多，进上下文的也永远只有当前这一个（加被提到的）。

## 控制台对话

人格模式左侧菜单里有两项：

| 菜单 | 行为 |
|---|---|
| **对话** | 和当前激活人格直接聊天；每轮写 raw（`source: "dsh"`，user + assistant 各一条），和私聊一样自动提炼记忆 |
| **对话测试** | 只读上下文；不写 raw、不提炼记忆，回复只用于测试（UI 里每条 assistant 都用红字标「测试模式」） |

两页都使用 SSE 逐字显示，底部是输入框，右下角是圆形 ↑ 发送按钮；Enter 发送，Shift+Enter 换行。

- 每个激活人格的普通/测试对话历史分别长期保存在 `console/chat`、`console/test` 的 `history.jsonl`，互不混在一起；每轮通过 DSH subagent 的 spawn child 执行，以继承 DSH 主会话的账户上下文，同时仍使用原灵自己的 preset。
- 工作目录固定在 `personas/<人格>/console/chat` 与 `personas/<人格>/console/test`，和记忆数据隔离。
- 两个 Agent preset：`yuanling-console`（正常）与 `yuanling-console-test`（测试）。测试 preset 额外挂 `dsh-yuanling/guard`，在每次工具调用时用 `tools.guard()` 拦住 Yuanling 的记忆写工具；只保留读上下文和本地 `fs`/`pwsh`。
- 人格初始化时自动创建 `app=dsh, account=master` 的「主人」人物卡；`dsh` 不出现在新建人物下拉里，也不能手动创建。它是控制台专用主卡，合并时始终保留主卡身份。
- 控制台聊天只允许回环地址 + console token；工具会真的执行，不要把这个页面暴露到公网。
- 管理台「框架 → 状态 → 大模型」可以切换 DSH 里已经配置好的模型；如果该模型声明了推理等级，会同时显示等级选择。选择存 `system/console-model.json`，点击「保存」后下一轮对话/对话测试都使用新模型，**两页共用同一个选择**。
- 也可以直接写 `system/console-model.json`：`{ "provider": "...", "model": "...", "reasoningEffort": "..." }`；`reasoningEffort` 可省略，省略时使用模型默认等级。

## 目的层：她惦记什么

活人感不来自"话说得多"，来自"心里存着事"。这一层只干三件事：**想要什么**（drives）→ **想说什么**（purposes）→ **这次说哪句**（selectIntent）。

### 存哪

| 文件 | 存什么 |
|---|---|
| `personas/<p>/self/drives.json` | 5 个内置需求的强度 + **她自己加的自定义动机**（含关键词）+ 最近刷新时间 |
| `personas/<p>/self/purposes.json` | 目的账本：`{id, need, text, origin, due, status, offered, hits}` |
| 卡片里的 `[惦记]` | 这一轮摆到她面前的 1~2 条（**不代表她说出口了**） |
| 卡片里的 `[动机]` | 强度偏高的那 1~2 条（用中文名，看得懂"她最近最想要什么"） |

### 需求：会涨，也会落

| 维度 | 变化 |
|---|---|
| 陪（connect） | **越久没和人说话越涨**（每天最多 +0.4，封顶 0.95） |
| 关心 / 好奇 / 分享 / 自我 | 各有基线，都按 **12 小时半衰期**回落到基线 |
| **自定义动机** | 自己给基线（默认 0.25），同样按半衰期回落 |

### 自定义动机：她可以自己加

模型能用 `yuanling_drive` 加一条自己的动机，**但必须给一组关键词**——"听到什么会更有劲"。

- 关键词在**消息入库时**撞上 → 这条动机升温（一条消息最多算 3 次，每次 +0.04）；
- 记忆里的事实撞上关键词 → 能长出**属于这条动机的**「惦记」（哪怕那句话本身很平淡）——
  这就是"更感兴趣的、接触更多的权重就会逐渐上升"落到实处的方式；
- 目的排序直接读这套强度，所以强度上去了，她真的会更常想起相关的事。

纪律：内置五个不能删；自定义最多 3 个（一共 8）；名字 ≤12 字；
调权重单次 ≤±0.2、一天最多 6 次、必须写 reason，全部进版本历史、可回滚。


为什么要回落：不回落的欲望会变成"永远黏人"。半个衰期后回到基线，她才有黏一阵、静一阵的节奏——**这是"像人"最省力的来源**。

### 目的：从记忆里挖，不从模型里问

一条事实要变成"惦记"，得同时满足：

- 创建于 **6 小时～7 天前**——刚说的不追问，陈年旧账不翻；
- 带情绪（`emotional ≥ 8`）或带槽位（`slot` 非空）——平淡的闲聊不记账；
- 同一份证据只惦记一次（按 `origin` 去重）。

生成的样子：`你上次说「面试没过，很难过」，后来怎么样了？`

**每条都挂 `origin` 指针**。被问"你怎么突然问这个"，能直接翻出那句原话——这是和 surfcore 最大的差别，它的素材是摘要，翻不回原文。

### 说哪句：三层过滤

| 过滤 | 拦的是什么 |
|---|---|
| 6 小时冷却（摆过或说过都算） | 刚出现又出现 |
| **真说出口 2 次** → 自动放下 | 一件事翻来覆去说 |
| **摆了 5 次一次都没接** → 也放下 | 这件事其实不重要，别再占位 |
| 一轮内相似 ≥ 0.55 只留一条 | 一次注入两条说的是同一件事 |

**「摆过」和「说过」是两个计数器**，这条是刚修的一个真缺陷：

> 以前注入时就把 `hits + 1`，于是模型压根没提，系统也认定"提过两次了"并自动放下（理由还写着"提过 2 次"）。她心里存着的事会**无声消失**，人还以为问过了。

现在：注入只记 `offered`；`hits` 只有模型显式回报才算——`yuanling_purpose {action:"mentioned", ids:[...]}`。放下时理由也分开写：`她说出口 2 次，可以放下了` / `摆了 5 次她都没接，说明不重要`。

所以一条惦记的生命线是有据可查的：**挖出来（open）→ 摆到面前（offered+1）→ 她真说出口并回报（hits+1）→ 真提满或是被判定不重要 → done/dropped**。`yuanling purpose list` 里同一个条目会显示"说过几次 / 摆过几次"，两个数字不一样才是正常的。

### 注入格式

```
[惦记] 你上次说「面试没过」，后来怎么样了？（想提就提，不想提就别提，别硬塞）
```

最多 2 条、每条 ≤120 字节，并且**明确写成可选**——宁可她不提，也不要为了满足提示而尬聊。

### 命令

```powershell
yuanling purpose list        # 账本（open / done / dropped）
yuanling purpose mine        # 从记忆里挖一遍
yuanling purpose drives      # 看当前需求强度
yuanling purpose close <id>  # 手动放下一件事
```

### 主动开口：核心只算，模块才发

没人说话的时候，她也可以想开口。这条链分两段，**核心只管前半段**：

```
动机够强 + 目的到期
   → 核心算"该不该说 / 说什么 / 发到哪"        → 待发队列（outbox.json）
   → 模块取走队列并真的发出去                     → 还没接（QQ 模块）
```

- **说什么**：到期目的 + 模板拼句，复述的是对方自己说过的事（不评价、不推销）；
- **发到哪**：**发在原话来的地方**——群里说的就发回那个群并 `@` 说话的人，私聊说的就发回那个人。
  不是统一甩给管理员（管理员并没有说过"面试没过"）；
- **闸门**：`rules.action.*` 全生效——`proactive=off` 不产出；`quiet_hours` 压着；
  `max_per_hour` / `max_per_day` 配额（`per_target` 决定按人还是全局）；群里默认不主动插话
  （`group_proactive=false` 时群里那几条进 `held`，你允许了就放出来）；
- **核心只算不投递**：队列写盘 + 记事件 `proactive.queued`。所以「人格 → 动机 → 待发的主动消息」
  里看到的是**她本来想说什么**，你可以逐条取消（记为 `dropped`，留着能回看）。
- **投递闭环（协议 v1.5）**：模块用 `outbox.fetch` 取走（`pending → claimed`），发完用 `outbox.ack` 回执
  （`ok:true → sent`；失败回 `pending` 重试，连续 3 次放弃；领了 5 分钟不回执自动回收）。
  **交给模块之前会重新过一遍闸门**（名单 / 主动开关 / 静默时段 / 配额），排队时合法不等于现在合法。
- **回复也要过核心（协议 v1.6）**：模块要主动发消息必须先 `egress.request`，核心查完
  `rules/action` + 名单 + 配额才放行；被拒只记原因、**正文不落盘**。
- **还没有任何模块实现这两步**：QQ 模块（独立仓库）在做，桌宠还没有。所以现在实机上"她算得出、没人送"。

节奏：默认每 **15 分钟**算一轮（`proactiveEveryMinutes`，0 = 关）。

## 安装

**它已经是 DSH 插件**：`index.js` 导出 `name / inject / Config / apply`，`package.json` 带 `dsh.bundle.patch`，包内的 `cordis.patch.yml` 负责把自己挂进 profile。

### 怎么装（三条路，任选一条）

**① DSH 设置里的插件管理（推荐，最不易错）**

DSH → 设置 → 插件 → 添加本地插件 / 安装 bundle，填仓库地址或本地目录。插件管理器会自动做三件事：写 profile 的 `dependencies`、跑 `pnpm install`、把包名加进 `dsh.profile.bundles`。

**② CLI（装了 DSH 命令行工具时）**

```powershell
# 直接按 git spec 装（⚠️ 必须带 `git+` 前缀：裸 https:// 会被当成 npm 包名去注册表找，必然失败）
dsh plugin --profile <profile> add "git+https://gitee.com/dshqqb/dsh-yuanling.git"

# 或先 clone 再装本地目录（最稳）
git clone https://github.com/dshqqb/dsh-yuanling.git D:\dsh-plugins\dsh-yuanling
dsh plugin --profile <profile> add "D:\dsh-plugins\dsh-yuanling"
```

> 两个仓库内容一致：**Gitee 优先**（国内可达），GitHub 作镜像。
> 桌面版 DSH 不一定带 `dsh` 命令；报"无法将 dsh 项识别为命令"时走 ① 或 ③。

**③ 手工改 profile（没有 CLI、也不想点 GUI 时）**

编辑 `<DSH_HOME>/profiles/<profile>/package.json`，两处都要加：

```json
{
  "dependencies": {
    "dsh-yuanling": "link:D:/dsh-plugins/dsh-yuanling"
  },
  "dsh": {
    "profile": {
      "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "dsh-yuanling"]
    }
  }
}
```

`dependencies` 只决定包能被找到，**`bundles` 才决定它被加载**——只加前者，插件不会启动。然后用 DSH 自带的 node/pnpm 跑一次安装（DSH 必须关着，否则文件被占用）：

```powershell
$node = "D:\Program Files\dsh\resources\runtime\primary-runtime\dependencies\node\bin\node.exe"
$pnpm = "D:\Program Files\dsh\resources\runtime\primary-runtime\dependencies\pnpm\bin\pnpm.cjs"
& $node $pnpm install --dir "$env:USERPROFILE\.dsh\profiles\desktop"
```

### 装完之后

**必须重启 DSH**。然后：

1. DSH 设置里出现「原灵」窗格（总开关 / 数据目录 / 管理台）；
2. 把数据目录指向你已有的库（例如 `D:\yuanling`），或留空用默认位置（首次运行会自动建骨架）；
3. 打开 `http://127.0.0.1:17777`，用设置页里的「复制令牌」贴进去，进管理台；
4. 想让模型真的用上记忆，再跑一次 `yuanling mcp install --root <数据目录>`（见下一节）。

### 配置项

**设置分两处：管理台四项在 DSH 设置页；其余运行设置在数据目录 `system/policy.json`。** 这样管理台地址/端口/局域网开关不会跟着人格数据被复制到另一台机器，而演化周期、主动开口、日志级别仍然随数据目录迁移。

| 设置 | 默认 | 改在哪 | 说明 |
|---|---|---|---|
| `enabled` / `dataDir` | true / 空 → `~/.dsh/yuanling` | DSH 设置页 | **这两个搬不走**：前者是总开关，后者决定去哪找数据目录（鸡生蛋） |
| `consoleEnabled` / `consoleHost` / `consolePort` / `allowRemote` | true / `127.0.0.1` / 17777 / false | DSH 设置页「原灵」窗格 | **管理台四项只在 DSH 设置里**；非回环必须先勾「允许同一局域网内的其他设备访问」 |
| `evolveEveryHours` | 6 | 数据目录 `policy.json` | 演化扫描周期（小时；0 = 关掉自动扫描） |
| `proactiveEveryMinutes` | 15 | 同上 | 主动开口周期（分钟；0 = 不算） |
| `autoApproveDays` / `dailyAutoLimit` | 3 / 1 | 同上 | 兜底默认值，人格规则里写了以规则为准 |
| `logLevel` | info | 同上 | debug / info / warn / error |

改法：管理台的「规则 → 运行设置」只改数据目录里的运行设置；管理台开关/监听地址/端口/局域网访问在 DSH 设置页「原灵」窗格里改。

> **搬机器时还剩两样要重配**：① `dataDir` / `enabled`（决定去哪找数据，不能存在数据自己里）；② MCP 客户端条目（写在 DSH profile 里，重装一次 `yuanling mcp install --root <数据目录>`）。其余全部跟着数据目录走。

### 接进 DSH（MCP）

记忆要真被模型用上，需要把它当工具暴露出去。yuanling 自带一个**零依赖的 MCP server**（`mcp-server.mjs`，stdio + 换行 JSON-RPC），提供**十三个**工具：

| 工具 | 干什么 |
|---|---|
| `yuanling_context` | 取回记忆卡 + `[惦记]` + 在场人物卡 + 当前群体卡（私聊/群聊都传 `channel`） |
| `yuanling_recall` | 按词检索记忆，返回事实、证据指针、**id 与 kind**（`extracted` = 机器摘的，可以用自己的话重写它） |
| `yuanling_account` | **写人物卡**：给 platform + nativeId 建卡，或改已有卡的昵称/描述；好友备注写进描述 |
| `yuanling_person_merge` | **合并卡**：把卡 id 列表合并成一个人物，成员表写进主卡（管理员那张优先，否则 id 最小）；账户权重/描述不动 |
| `yuanling_person_split` | **拆卡**：把一张卡从主卡成员表里移出，成为独立人物 |
| `yuanling_observe` | **写 / 读印象**：账户描述和群体描述共用一套（整段覆盖 + 必填 reason + 版本历史；账户 2000 字符、群体 600 字节）；`withHistory` 能看这份印象一路怎么变的 |
| `yuanling_purpose` | 看 / 回报**惦记**：`list` 读账本；`mentioned` 回报"我问过了"（不回报系统会以为你没提）；`drop` 回报"这条不提了" |
| `yuanling_group` | 看 / 改某个群的名字；只给 `channel` 就能定位是哪个群，只读时不建档 |
| `yuanling_drive` | 看 / 改**动机**：`list` 读强度；`adjust` 调权重（≤±0.2/次、6 次/天、必填 reason）；`add` 加自定义动机（必须给关键词——听到那些词才会升温，也能长出属于它的惦记）；`remove` 删自定义动机 |
| `yuanling_remember` | **用她自己的话写一条事实**：必须给 `src` 指针；可用 `supersedes` 替换掉自动提炼的那条（旧事实不删、不再进上下文）；重复的表述只 +1 次数 |
| `yuanling_sources` | 看已装模块里有哪些数据能被她**主动要**（v1.1：模块声明 `sources` 才有） |
| `yuanling_fetch` | **取一次数**：向某个模块要数据，**先落原始层再给她看**，所以查过就记得；一次最多 20 条 |

**用一条命令登记，不用手改 YAML：**

```powershell
yuanling mcp install --root "D:\yuanling"   # 自动找到 profile 写进去（幂等）；--root 指定读哪份记忆
yuanling mcp status                          # 看装没装、路径对不对
yuanling mcp uninstall                       # 整块摘掉，其余配置原样保留
```

`--root` 很关键：它会被写进 `args`，MCP 服务器就用这份数据。**不传的话吃 `YUANLING_HOME`，再不然用默认位置**——默认位置若没 `init` 过，工具会报"数据目录不可用"。

多 profile 时加 `--profile <名字>`；profile 不在默认位置时用 `--dir <目录>`。改完**重启 DSH** 才生效。

它写进去的东西长这样（标记内由命令维护，标记外是你的地盘）：

```yaml
# === yuanling MCP BEGIN ===
# 由 `yuanling mcp install` 维护；整块会被替换，请勿手工编辑内部条目。
- insert:
    - id: mcp-yuanling
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: yuanling
        transport: stdio
        command: '<node 的绝对路径>'
        args:
          - '<仓库里的 mcp-server.mjs 绝对路径>'
          - '--root'
          - '<数据目录，如 D:\yuanling>'
        toolCallTimeoutMs: 30000
# === yuanling MCP END ===
```

> 为什么需要命令而不是手改：条目里含**绝对路径**（每台机器都不同）；手改的东西没有幂等保障，重装、换 profile 就会丢；卸载时用户也不知道该删哪几行。写前会留一份 `cordis.patch.yml.bak-yuanling`。
>
> 为什么不直接用插件钩子：DSH 给插件的入口只有「排队一个回合」（`sessionController.prompt`），那会把 `[惦记]` 变成一条"用户说的话"，污染对话记录。MCP 是干净的读通道——模型按需调用。
>
> **它有个隐性依赖**：模型不一定每轮都会主动调工具。目前的做法是把工具描述写得足够强硬（`【每轮必调】…不调用就等于失忆`），外加 `initialize` 里的 `instructions`——**不碰宿主预设提示**。观察几天，真不调再考虑升级。

### 设置页（DSH 设置 → 原灵）

装好插件后，DSH 设置里会多一个「原灵」窗格。它只放**该放在设置里的东西**，其余一律留在管理台：

| 项 | 说明 |
|---|---|
| **总开关** | 开 = 注入 + 写记忆 + 起管理台；关 = 三样全停，数据原样保留 |
| **数据目录** | 可改。旁边直接显示体检结果（可写 / 已初始化 / N 条事实）；**改目录会自动同步 MCP 条目的 `--root`**，然后提示重启 DSH |
| **管理台** | 开关、监听地址、端口、是否允许同一局域网内的其他设备访问；非回环地址必须先勾选允许局域网访问 |
| **打开管理台** | 一键跳转 |
| 状态摘要 | 激活人格、事实数 |

两个设计取舍：

1. **管理台开关跟着机器走，不跟着人格走。** 管理台开关/监听地址/端口/是否允许局域网访问在 DSH 设置里；运行设置（演化、主动开口、日志）在数据目录里。
2. **运行设置的真相在数据目录。** 设置页只负责宿主级参数；人格规则与运行设置仍以数据目录为准，两边不重叠。

客户端半边（`web/client.js`）是**预打包**的浏览器模块：`window.__ModuleLoader__` + `require('react')`，手写 `h()`，**没有构建步骤**；由 `package.json` 的 `dsh.client` 交给宿主加载。

### 设置里看不到「原灵」时（修复注册）

DSH 桌面的启动失败对话框里有一个「**禁用第三方插件、备份 profile patch 并重启**」按钮。它是救急用的：
会从 profile 的 `package.json` 删掉第三方 `dependencies`、从 `dsh.profile.bundles` 删掉第三方 bundle、
再把 `cordis.patch.yml` 里的第三方条目清空。**按一下，原灵就从设置里消失，而且之后不会再被加载**。

注册靠的是 `dsh.profile.bundles` 里的 `dsh-yuanling` 这一项——profile patch 里那条 `- id: dsh-yuanling`
只是**对已存在条目的配置覆盖**（`dataDir` / `enabled`），条目本身来自插件包自己的 `dsh.bundle.patch`。
所以只补依赖或只补 patch 都不够。

```powershell
yuanling repair --dry-run     # 先看它要补什么（不写盘）
yuanling repair               # 真补：依赖 + bundle 注册 + node_modules 软链 + 配置条目 + MCP 条目
```

它会自动找 profile（提到原灵的优先，其次 `desktop`）和 patch 里原有的 `dataDir`；有多个 profile 时用
`--profile <名字>` 指定，`dataDir` 被整段清空时用 `--data-dir D:\yuanling` 补上，`--no-mcp` 可以不动 MCP 条目。
命令幂等（再跑一次会说"本来就是好的"），写前备份成 `*.bak-repair-<时间戳>`。**改完要完整退出 DSH 再启动。**

另外，若 DSH 启动直接报 `desktop welcome: Web authentication failed`，那是**桌面端自己的会话问题**
（本机 launch token 没通过），和原灵无关，也不需要 `repair`：先彻底退出所有 DSH 进程，
再删 `%APPDATA%\@deepseek-ai\dsh-desktop\Network\Cookies`（连同 `Cookies-journal`），然后启动即可——只会让你重新登录，不动任何数据。

## 管理台

`http://127.0.0.1:17777` —— 顶栏可切「核心 / 模块」与明暗主题。

- **核心**：状态 / **注入预览** / 记忆 / 条目 / 提案 / 人物 / **群体** / 规则 / 用量 / **来源** / **日志（含审计）** / **诊断** / 拒绝记录
- **模块**：控制台（数量 + 安装框）+ 已装模块列表；点进模块是 tab（概况 / 日志 / 审计 / 诊断 / 模块自定义只读页），概况里有能力授予开关、配置表单、导出 / 停用 / 卸载

**人物页**：三段（管理员 / 重要人物 / 好友）；新建人物是「App → 账户 → 昵称」；卡片后面的「账户 xxx」只改那一个账户，
点卡片本身改这个人物（昵称 / 描述 / 权重 / 重要 / 名单，以及把合并进来的账户**分离**）；「合并」是两级选择，一次请求取齐候选。

**群体页**：新建「App → 群号 → 描述」；编辑里能改 App/群号（改号会同步身份登记，`gid` 不变）、改描述、
一行一个成员（`第一个昵称 · app:账号`）可移除，下面用「App → 账户」把人加进来（上限 60）。

「来源」页回答两件事：**谁还在往这里投递**（心跳，沉默的会标红），以及**模块能给她提供什么数据**——每个 source 被取过几次、最近一次取数是什么时候、那条记录落在 `raw/` 的哪一天。后者是从原始层数出来的，不另记账本。

### 日志与审计：一条流，两个镜头

日志和审计不是两件事，是**同一批数据的两种问法**：「刚才发生了什么」和「谁改了她的记忆、为什么、能不能退回去」。

| | 存哪 | 是什么 |
|---|---|---|
| **日志** | `system/log/events.ndjson` | 运行流水：投递、摄入、模块启停、能力授权、拒绝、错误 |
| **审计** | `system/versions/journal.ndjson`（正本） | 每一次写盘：谁（`model:*` / `human:editor`）、为什么、改前是哪个 hash |

页面只有一个，顶部一排筛选：**全部 / 只看写入 / 只看异常 / 只看模块 / 只看拒绝**——「只看写入」就是审计，每行带路径与原因，还有一个**回滚**按钮（回滚本身也记一条新版本，不擦掉后来的历史）。

事件流**不是正本**：删了它，审计照样完整（审计直接读版本 journal）。所以不存在"两个真相来源"，也不会有"日志写丢了，回滚记录也没了"这种事。轮转 1MB × 5 份、留 90 天；写不进去不会挡住任何业务，但会在诊断里报出来——**审计写不进去本身就是一条要看到的诊断**。

审计行带 `ref`（版本 hash）。没有回滚入口的审计，只是另一种日志。

### 诊断：每条给下一步

诊断借鉴了 surfcore 的做法：不是把日志贴上去，而是每项拆成 **`{code, stage, level, hint}`** —— 错在哪、哪一步、**下一步做什么**。比如日链断了会直接给 `yuanling verify` 那条命令。

三层来源并成一张清单：

1. **核心自检**（复用 `doctor` 的检查），每项映射到一句可执行的建议；
2. **模块事实**（核心知道、模块自己不知道的）：没握手 / 崩过 / 声明了能力却没授 / 配置过不了 schema；
3. **模块自报**（协议 v1.4 的 `diag.report`）：cookie 过期、上游限流这类只有模块自己看得见的事，带 `source: "module"` 标进来。

两条纪律：**不假绿**（模块自报有 15 分钟 TTL，进程死了它上次报的"正常"必须消失）、**只读**（诊断不会自己去修——顺手改数据的诊断，出事后你分不清是不是它修坏的）。

空就是空：没有问题时页面显示「没有需要处理的事」，并且可以切到「全部检查项」看见**它到底查了什么**——一句"一切正常"说明不了任何事。

模块的「日志 / 审计 / 诊断」三页由**核心统一提供**，模块不用改协议：日志是它的 stderr 加核心写的生命周期，审计是它造成的写入，诊断是核心事实加它可选的自报。这样十个模块是同一种形状，页面才筛得动。

窄屏时侧栏收窄但不隐藏文字（模块名必须看得见）。

视觉骨架参考了一套 Figma 管理台：靠底色分层（浅色卡片浮在灰底上、暗色卡片浮在近黑底上）、20px 圆角、不做 1px 描边、只有主数字卡用高饱和渐变。图表的装饰一件没抄——没有真实时序数据，画假图比空着更糟。

第一次打开要粘贴 `system/secrets/console.token`（存本机 localStorage，只发给回环服务）。写操作都要 token，服务端不返回 CORS 头，别的网页发不进来。

**注入预览**是最有用的那一页：它显示"这一轮她到底读到了什么"。记忆系统最大的问题不是不记得，是**你以为它记得**。

「用量」页只报**能算准的东西**：每天真实的消息条数与字节、当前卡片体积、按字节换算的估算 token（±30%）。费用一栏明写"未接入"——模型侧的真实用量要宿主给，猜出来的数字比没有更糟。

## 安全边界

- 默认只听 `127.0.0.1`；只有勾选 DSH 设置里的「允许同一局域网内的其他设备访问」后，监听地址才可以填非回环地址，且启动时会打警告。
- 控制台令牌独立于 DSH，重装数据目录即失效。
- 不联网、不引第三方运行依赖（只有宿主提供的 `@deepseek-ai/schemastery`）。
- `personas/<p>/entities/cards/` 视为敏感：不导出、不进注入；只有当前在场的那几张卡会进上下文。

### 文档在哪

分两类，**别放错地方**：

| 目录 | 给谁看 | 是否随仓库发布 | 放什么 |
|---|---|---|---|
| `doc/` | **用户和开发者** | ✅ 是（`files` 里有） | 协议、设计分析、安全说明 |
| `ref/` | 只有我自己 | ❌ 否（`.gitignore` 已忽略） | 待办清单、故障复盘等过程材料 |

`doc/` 里现在有：

| 文件 | 讲什么 |
|---|---|
| [`doc/MODULES.md`](doc/MODULES.md) | **怎么写一个模块**（教程）：包结构、`yuanling.module.json`、信封与 op、能力、本地装上调试、自测清单、发布 |
| [`doc/PROTOCOL.md`](doc/PROTOCOL.md) | **规范**（v1.0 已冻结）：信封、方法表、错误码、能力协商、超时表、`§17` 七条验收单 |
| [`doc/PURPOSE_ANALYSIS.md`](doc/PURPOSE_ANALYSIS.md) | surfcore「目的层」的拆解，以及原灵学了什么、改了什么 |
| [`doc/SECURITY.md`](doc/SECURITY.md) | 安全边界：暴露面、密钥处理、越权防护 |

**协议与教程为什么分开**：协议是冻结的契约（改要升 `api` 次版本），教程会随实践更新。合并成一份，每次改教程都得重新论证"协议变没变"。

`ref/` 里是给自己用的过程材料，原则和代码一样：**记事实、标确定性等级，不记口号**

| 文件 | 作用 |
|---|---|
| `ref/WORKLIST.md` | **还没做什么**。按模块分节的待办与技术债。改代码前先看它 |
| `ref/UPDATE-INVESTIGATION.md` | **一次故障的完整复盘**。DSH 应用内更新在 Windows 上静默失败（`graceful deadline exceeded` + 安装器目录交换失败）的排查过程：现象、证据、对照组实验、根因（安装器继承了"安装目录"作为 cwd）、修复与验证清单。它同时证明"那次失败不是原灵引起的" |

更新 `ref/` 时保留证据（命令、输出、时间），下次遇到同类问题能直接复用。

### `examples/SELF.md` 是做什么的
